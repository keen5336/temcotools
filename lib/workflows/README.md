# Workflow kernel integration

This directory supplies a bounded declarative interpreter and an executable, **synthetic-only** Receiving practice adapter. The pure kernel performs no HTTP, database, WMS, printer, camera or Scan Lab calls. The separate `service.ts` authorizes/persists runs and reuses registered internal inventory lookup/observation services in `application` mode; see [workflow-domain-actions.md](../../docs/v2/workflow-domain-actions.md). The kernel is not an authorization service or a job dispatcher. Nothing here qualifies an upstream mapping, physical print, receipt or closure.

`definition.ts` exports `validateWorkflowDefinition`, `validateWorkflowFields`, `readWorkflowValue`, `mapWorkflowParameters`, `evaluateWorkflowCondition`, JSON helpers and the corresponding Zod schemas/types. Definitions contain at most 40 forward-only steps: typed form, exact-unit/quantity scan, explicit human/camera/device/approval confirmation, condition or named action. Expressions read literal values, run data or earlier step output through bounded own-property paths. They cannot execute code, fetch a URL or dynamically select an action. Missing values fail comparisons and required mappings. Conditions use `all` over bounded comparisons; branching is forward-only and skipped steps remain recorded. An author must explicitly point a branch past the alternative branch when appropriate.

`engine.ts` exports `createWorkflowRun`, `advanceWorkflowRun`, `workflowReadiness` and run/command/result/provider/action types. A transition returns `{ run, intents, replayed }`; it never sends an intent. A creation may immediately return its first intent. Commands require an exact definition version, expected run revision and stable command ID. Replaying the same complete command envelope returns its original revision/intent references, **without re-emitting intents**; reuse with changed content conflicts. Completed runs are immutable. Definitions, action versions, configuration version, originating site and exact provider/configuration/grant bindings stay pinned. New publication or a UI warehouse switch cannot retarget a run.

The server must load persisted state and build `WorkflowRuntime` itself after current authentication, active warehouse membership, capability, OAuth scope, run ownership/delegation and site checks. Do not accept a runtime, run snapshot, provider readiness, grant, result or synthetic actor from a UI/MCP body as authority. `runPermitted` is a current execution decision, not a cookie role. `actorUserId` and `now` are server values. The UI and MCP use the same application commands. Provider snapshots must represent the actual upstream identity/warehouse and current named-action grant; connected transport alone is insufficient. The exact original provider is required; another connected session is never an implicit fallback. The `origin` executor/reconciler distinction is a trusted service boundary, never a caller-selectable role.

Minimum durable records:

- Immutable `WorkflowDefinitionVersion` with validated JSON, draft/published/disabled lifecycle and author/publication attribution. The kernel validates content; the surrounding service enforces publication authority, site/platform template overrides and only published versions for ordinary runs. A disabled version/action can block future dispatch without rewriting history.
- `WorkflowRun`: site, definition/version, configuration version, original actor, revision, status, current step and persisted JSON snapshot. Provider bindings and data are within that snapshot. Runs stay site pinned; do not expose another site's state through ID lookup, exports or jobs.
- Unique `(runId, commandId)` command receipt and expected-revision compare-and-swap, committed with the updated run. The kernel retains bounded in-snapshot receipts for practice; production services may normalize them without changing replay semantics. Preserve the canonical original envelope including its original expected revision.
- Unique intent ID / `(runId, stepId, attempt)` outbox row, with the complete returned pins, requester, provider owner/device/session and later worker/run/step attribution. Commit the run and outbox **before** any dispatch. A competing writer that loses CAS must not dispatch its locally calculated intent.
- Append-only observed scan, step, intent dispatch/result and reconciliation audit records. Retain original result receipts and partial results before updating the run snapshot; the snapshot alone is not an immutable external-effect ledger. Persist the separate synthetic Receiving state/results with its corresponding run transition in the same transaction.

Immediately before outbox dispatch, recheck current membership, scopes/capabilities, original provider/grant, site, lease/upstream identity and pinned published action/configuration. Validate mapped parameters against that action's actual input schema. The kernel produces plain JSON mappings; the approved integration adapter remains responsible for its typed output/request contract and effect policy. A queued intent is not continuing authority. Claim dispatch once through the existing durable intent/job service and use its supported idempotency/reconciliation behavior. Never hot-swap code or resend after unknown contact/results. For pending result capture, trusted services may retain evidence after revocation while the next action remains blocked; no new operational work is granted by that exception.

Readiness separates start prerequisites from current-step dependencies and returns red/yellow/green reasons plus fixes. Once started, a lost start-only dependency does not retroactively prevent unrelated later steps; current execution authority always applies. A scan can buffer during provider-only failure **only** when its definition explicitly permits it. It still has a finite capture limit, cannot bypass membership/capability failure, and cannot finish a blocked step. No background inference queue exists here. Pause prevents new dispatch, including when an already pending result arrives. Human/device handoff retains the original intent; refresh/resume do not issue another. A human confirmation is an attributed claim, not fabricated device/camera or physical-effect telemetry.

Known failed actions retry only with explicit definition opt-in, a separate bounded command, and a read effect or trusted no-effect proof; at most three attempts. Unknown results only accept a trusted, attributed reconciliation of the retained intent with a known result. Results and discrepancy resolutions require server current authority outside this pure module. Scan event IDs are stable; repeat identifiers on separate events preserve duplicate evidence, quantities do not double count, ambiguous identifiers require an exact candidate, and a reviewer resolution does not manufacture a missing unit.

`receiving.ts` exports `SYNTHETIC_RECEIVING_DEFINITION`, `SYNTHETIC_RECEIVING_DELIVERY`, `SYNTHETIC_RECEIVING_BINDINGS`, `createSyntheticReceivingRuntime` and `executeSyntheticReceivingIntent`. The runtime factory is **demo/test-only** and explicitly grants only local simulated providers; never use it to authorize a live action. Use `createSyntheticReceiving` and the exact-unit scan/request/settle/reconcile helpers to retain the practice state. The executable flow selects the fixture delivery, obtains two exact unit slots, scans each, retains discrepancies/duplicates, prepares simulated label ACKs, requires a separate confirmation, records individual simulated WMS receipts and permits closure only when every required fact is confirmed. Label ACK, physical confirmation and WMS receipt are independent states. Unknown unit results retain successful siblings, and unknown close blocks another close. IDs/barcodes are synthetic. No software result in this exercise is a real print, receipt, presence or delivery proof.

`LIVE_RECEIVING_QUALIFICATION_NEEDED` lists the narrowly missing identity/site/read/line-unit/receipt/close/label evidence and live-trial authority. Qualified live adapters must implement those actual contracts; do not infer them from this simulator or Route Planner/DMP identifiers. Experimental OCR output is not wired into Receiving.

Validation: `dev-run -- npx tsx --test scripts/workflow-kernel.test.ts` exercises real in-process interpreter/simulator transitions and failure paths. It does not qualify live providers, browser UI, MCP wire, hardware cameras or Zebra performance. Defaults bound definitions, JSON, scans, attempts, commands, events and operation buffers; services should split large operational batches instead of increasing them implicitly.
