# Platform defaults and warehouse overrides

Open `/management/templates` to manage protected platform source and the current warehouse's allowed overrides. The same services are available as `templates.list`, `get`, `save`, `publish`, `rollback`, `enabled`, `preview`, `adopt` and `detach` through UI/MCP. `sites.defaults` supplies current selection defaults without creating operational authority.

Platform administrators with current `platform.manage`, password and MFA confirmation within 10 minutes can save/publish/restore/disable reusable source. Published versions are immutable and contain a reviewed display title, content hash and attribution. Ordinary warehouse people receive published source and their own retained pins; private drafts and mutable draft names are excluded. No global template may contain credential/header/cookie material, customer fields, person/session/grant IDs, actual device/provider/printer IDs or printer endpoints. Publication also requires explicit review of the source and name for private data. A template cannot grant a capability or qualify an upstream adapter.

Three typed kinds are implemented:

- **Workflow** uses the existing bounded workflow validator. Platform action/configuration/mode/permission/completion controls stay fixed. The platform policy may permit a local name and operator-facing step text. Adoption creates actual current-site `WorkflowDefinitionRecord` and immutable `WorkflowDefinitionVersion` rows; the existing mobile workflow tool starts those versions normally. A later source publication does not change a warehouse binding until explicit adoption, and new local publications do not rewrite active run snapshots.
- **Label workflow** uses the existing label validator and version hash. Platform purpose, required fields and rules stay protected; policy may permit name/ZPL/media changes. Adoption creates actual current-site label workflow/version/audit records. The existing evaluation/issuance consumers use that publication. A platform label source's purpose is permanent; choose a separate template for another purpose. Existing local labels require their current revision plus explicit replacement before first adoption. No label is sent or physically confirmed by adoption.
- **Warehouse defaults** supplies timezone, locations, optional managed-printer name, optional legacy label-workflow purpose and explicit connection-selection rules. Allowed site overrides may replace fields or choose a local managed printer ID. Adoption materializes real `WarehouseSite.configuration` values. Operator printer configuration resolves the exact local default first, scanning uses the location choices, and connection status exposes the declared rules. A global printer name is resolved only within the adopting warehouse; a missing/ambiguous match creates no other-printer fallback. The legacy `defaultWorkflowId` setting continues to mean `LabelWorkflow.purpose`, not an operational workflow ID. Connection rules require an explicitly authorized provider and never install/pair/sign into a system, create a grant or silently select another person's session.

Choose a published source/version, enter only allowed override JSON and select **Preview permitted overrides**. The preview shows effective content and the current native consumer revision. Adoption requires the corresponding current `workflows.manage`, `labels.manage` or `sites.configure` capability plus recent password/MFA, the binding revision, consumer revision and a reason. Review and explicitly allow replacement when existing local values would change. Global/warehouse/binding revisions and durable operation receipts prevent stale edits and lost-response retries from producing another adoption. A site cannot edit another site's binding or inherit a foreign printer ID.

Native workflow/label/settings editors guide inherited-copy edits back to this override manager. Their guards share the native consumer lock order with adoption, so a writer cannot pass an inheritance check before adoption and later overwrite protected materialization. Only fields declared by the pinned platform policy may change. Detachment requires platform authority or an explicit `allowDetach` policy; it retains the native consumer and historical versions as a local snapshot. Retiring a global source stops future adoption without retroactively rewriting existing warehouse copies or historical runs.

Persistence uses protected global draft/version records and forced-RLS site bindings. Migration 36 adds the records, platform fresh-MFA write policies, immutable versions and source-link checks. Additive migration 38 fixes the shared source-link trigger's table-specific field resolution; 36's checksum is unchanged. The service verifies source hashes, capability/warehouse authority and local consumer references before materialization. Model/payload declarations are data, with no eval, arbitrary request execution or copied relay credentials.

`scripts/templates.integration.test.ts` exercises real disposable PostgreSQL services: platform-versus-site authority, MFA/RLS denial, draft privacy, distinct site overrides, real workflow/label/default consumers, pinned old runs, protected native writes, explicit local printer selection, current membership revocation and adoption/native-write concurrency. Fixtures contain synthetic people/data and invalid printer destinations; no live warehouse/provider/printing operation is invoked. Actual printer/device/upstream contracts remain separately qualified. This package supplies reusable workflow/label/default inheritance and explicit selection rules; it does not introduce a global directory of operational printer/device/session objects or grant those objects authority.
