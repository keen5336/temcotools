# Connecting an approved work-browser provider

This guide describes the generic provider software being integrated after runtime7d. Check [build status](build-status.md) for its actual deployed revision. The existing DMP relay and its bookmarks remain independent and usable. No Route Planner/WMS/MARS identity or action contract is qualified by this guide or by a synthetic fixture.

The work machine keeps its upstream login. The v2 server and an MCP client never receive that site's browser cookies, auth headers, browser storage or a copied session. Install the one **Connect TemcoTools** bookmarklet from the payload/site manager, then run it on a supported page. Only origin and pathname are dispatch metadata; query/fragment/DOM are not collected. An unsupported, ambiguous, disabled or unpublished mapping performs no operational work. Normal site CSP must permit the injected script and socket; the app does not bypass it.

For the existing DMP workflow, use **Load current DMP executor**, save/publish deliberately and map its exact origin. Its named operations and explicit per-client read sharing retain their existing controls. Generic provider grants never authorize the old DMP connection, and a DMP connection/grant never authorizes another integration.

For another approved integration, an administrator first prepares:

1. Typed named action versions with actual evidenced endpoint/request semantics, response schema, limits and required capability. A query may use POST only when its semantic read classification is supported by evidence. No arbitrary URL, header, projection or code execution tool is exposed to ordinary users/MCP.
2. A published **generic approved-provider executor** payload, its exact target origin and approved action keys (including the identity action). Publish the exact origin/path mapping. Routine mapping/action edits are managed data; new identity parsers/protocols can require reviewed adapter code.
3. A warehouse-local provider configuration with its exact identity action/version, actual JSON subject/warehouse field paths and evidenced upstream warehouse. This pins the immutable payload/profile/action/config versions. Synthetic qualification cannot become a pilot/live contract by changing a UI option. XML business bodies are accepted as bounded text; XML identity extraction still needs a separately reviewed parser.

The human signs into the upstream page and presses **Connect this tab** in its injected panel. In the Temco popup, sign in as yourself, choose the reviewed provider for the current warehouse, and approve that original tab. The page independently checks actual origin/path and all returned immutable pins. The relay then performs the approved identity read; transport connection alone is not authentication or action readiness. No upstream login or sharing consent can be performed by MCP.

Once established, the provider tab may remain open independently of the Temco tab. Its bounded heartbeat rechecks the original individual session/membership/configuration and refreshes only the approved identity read. Background throttling, lease expiry, session revocation, page/identity change or network failure can require an explicit reconnect. No business work is retried or moved to a spare tab. A replacement payload cannot replace an in-flight operation.

Access from another session/device or MCP requires an explicit, expiring named-action/effect grant from the human provider owner. Same-account login and a same-person device link alone create no execution authority. Read sharing and write execution are separate, and printer delegation is a different physical-effect permission. The requesting user/client must still have current warehouse membership and the action capability. A device default routes to a specific approved provider; it does not confer permission or permit silent failover.

In **Connections**, prepare an action with a stable operation ID, then dispatch that original queued intent. The receipt is committed before socket send. Inspect its private result using the same application query through UI or scoped MCP. A correlated HTTP response means `reported`, with separate declared-output validation; it does not prove warehouse receipt, delivery, printing or business success. Raw bodies remain private. Unknown, timed-out or disconnected outcomes are never replayed automatically. An original queued intent can be retired while offline; uncertain work requires current office authority, fresh authentication and actual evidence. Resolution preserves the original receipt and requires explicit reconnect.

The pilot still disables all live warehouse/WMS/MARS/print effects. To qualify an actual new integration, provide private body-only identity and named-read examples with source/as-of/method and the relevant screen/action; do not upload Cookie/STKN/header/HAR material. Existing private JSON/CSV/XML intake can establish field evidence without claiming a live adapter. Official Ashe finals remains separately unqualified. No operator needs to provide every edge case before independent software work can continue.
