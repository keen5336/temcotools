## Migration, compatibility and cutover

### Add before replacing

Use additive tables/columns and migration steps. Keep current IDs, source rows, submissions, audit sessions/reports, scans, archived waves/recons, printer definitions, templates, favorites and files. Do not rename/drop existing fields just to obtain cleaner v2 terminology. A compatibility adapter should read old records and call the new shared services; avoid independent bidirectional dual writes. Where two stored projections must coexist, write them in the same transaction from one command and record a checkpoint for safe backfill.

Backfill can run in bounded restartable chunks with old-record ID as an idempotent key. Report counts and unresolved mappings before cutover; do not mutate production under the source build mandate. Full backups and a verified restoration procedure precede eventual production migration. Source history, actual data backups and diagnostics belong in protected external storage, not this public repository.

Maintain full source rows privately. |

Do not migrate inferred DMP histories from displayed receipt text or invent a MARS API from label-page scraping. Where prior data is unavailable, show “history available from…” with the real starting point. Resolve high-confidence links automatically only after source rules are qualified; provide an authorized review path for all other links.

### Control effect execution once

Before either UI or MCP can dispatch a print/MARS mutation, persist its operation ID and input/version/authority with uniqueness constraints. Serialize competing creation attempts for the same unit/intent. The requester's retry key maps to that record; reusing it with different inputs rejects. Guard command version/preconditions inside the writer transaction. Recheck identity, authorization and current disposition before dispatch. Receipt/status reads and retries recheck current user/client/object scope; a guessed operation ID is not authority. Cookie-authenticated UI mutations also require exact-origin/CSRF checks. External transport boundaries cannot provide an exactly-once guarantee; a crash after send leaves `outcome unknown` until reconciled. Do not recover by blindly resending.

Observation ingestion can safely replay the **same captured event ID** to obtain its original receipt. It is distinct from replaying an external action. Rescans are new evidence but cannot double-count a unit's allocation or current finals credit. Label content generation and device delivery are separate: a device reports what it actually did, not what the server hoped happened.

### Cut over by workflow, with explicit rollback limits

1. Develop with synthetic data in a separate database/composition. Validate migrations/backfill on a disposable representative dataset; preserve failure diagnostics, without adding an elaborate evidence platform.
2. Using available authorized read-only evidence, compare old/new WMS views and new DMP worklists read-only against supported private samples and actual official finals. Resolve differences in domain rules, not by copying a customer's payload into Git.
3. Establish strong identity/recovery and complete retained-action UI/MCP parity before a v2 pilot. Select an authorized workflow/cohort, preserve current tools as fallback and prevent two execution paths from independently dispatching the same effects. Enable flags for behavior rollout, not as a substitute for server permissions.
4. Qualify the exact Zebra browser/scanner and direct/laptop printer paths. Demonstrate the finite operational scenarios with the people doing the work. Obtain owner acceptance for workflow/role choices; separately obtain deployment and any live mutation authority.
5. Retire Report Engine and redundant entry points only after useful replacements and retained exports/history are accessible. Mark legacy pages with a destination first; delete data only under an explicit retention decision. Update orientation docs to the actual final runtime at that point.

`v1` preserves source, not a full database rollback. Prefer an additive rollback that disables v2 execution and routes to compatible existing views. Current [deployment script](../../scripts/deploy.sh) requires clean published `main`; pushing `v2` must not trigger a deployment or changing that guard. A later release needs an explicit promotion/release plan. Verify old binaries can tolerate the additive schema; credential cutover and new external effects may make a simple binary rollback unsafe. Do not restore old PIN-only public login as the default recovery strategy, and do not restore a database snapshot over newly created physical/external evidence. Keep operation records and reconcile in-flight/unknown work before rollback or forward repair.
