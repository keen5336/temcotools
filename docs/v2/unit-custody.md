# Controlled warehouse custody

Owner requirement: preserve one physical unit and its aliases across warehouses, while keeping each warehouse's private operational history private. Original and replacement appliances remain different units. This package adds local planning/evidence commands; it calls no upstream system and performs no printing. Physical departure/check-in commands are explicitly unavailable in the isolated pilot.

## Records and privacy

Migration `20261103190000_unit_custody` preserves every existing `WarehouseUnit.id`. Its immutable `siteId` records origin, not present physical custody. Compatibility creation fields remain in Prisma but the database moves their values into site-private `WarehouseUnitOrigin` and stores NULL on the shared identity row. Native creators can keep supplying those fields; idempotency/detail consumers read the origin relation in their own site context.

`WarehouseUnitSite` gives a warehouse explicit association with that identity. Backfilled associations are `unestablished`, not inferred stock. Proposed movement does not give destination lookup rights; acceptance adds `expected` participation. Departure changes source to `departed` and destination to `in_transit`; only independent destination check-in establishes its recorded custody. A partial unique index permits one confirmed custodian per unit. Historical participation permits own-site history, not execution elsewhere.

`WarehouseUnitAlias` holds only immutable kind/namespace/value/unit and current revocation/revision. Existing `WarehouseIdentifier` retains raw value, private evidence and attribution under original RLS. `WarehouseUnitAliasVisibility` shares exact approved aliases per site; new aliases added later do not appear at former sites. A transfer pins approved `{id,revision,kind,namespace,value}` snapshots. Revocation is detected before physical transitions. No identifier is assumed globally unique; order numbers never identify or merge units.

`WarehouseUnitTransfer` contains the two participating sites, exact unit, state/revision, approved alias snapshots and bounded handoff fields (`description`, `handlingInstruction`, `reference`). It contains no copied source rows, customer payloads, private notes, office authority, provider grants or label authorization. A former site cannot read a later transfer between other warehouses. Its events/command receipts remain site-private and append-only. Every command retains original actor/session and immutable same-operation results.

Inventory source rows are now unique by `(siteId,lpn)`. Report import is still reported state, not physical movement. The native importer must use `getPermittedImportedIdentityInTransaction`: a current visible exact WMS alias can bind a destination report row to the existing ID, including accepted-but-not-yet-arrived freight. Foreign or ambiguous matching aliases return only `{unitId:null, conflict:true}`; retain a review item/unassociated row, never auto-create a duplicate identity. The helper discloses no foreign identity or warehouse details.

## Shared service/UI/MCP contract

Services in `lib/warehouse/custody.ts` accept a verified current `Principal`; the application adapter supplies `withPrincipalSite`. Commands require current `inventory.custody` in their transaction. Built-in warehouse-manager receives that capability; ordinary operators do not receive it automatically. OAuth scopes remain an independent ceiling.

- `listCustodySites`: minimal selectors for the person's current custody-capable memberships (platform admins may select active sites). A receiver may separately supply an exact destination ID. Validating that exact ID exposes only its name/ID, never membership or stock.
- `proposeUnitCustody(custodyProposeInput)`: exact unit/destination, approved alias IDs, bounded handoff and own-site note. Returns `{transfer,replayed}`.
- `acceptUnitCustody(custodyActionInput)`: destination's current authority; expectation only.
- `departUnitCustody(custodyPhysicalInput)`: source's current authority after acceptance; requires a separately persisted source `departure` observation.
- `checkInUnitCustody(custodyPhysicalInput)`: destination's current authority after departure; requires a separately persisted destination `check_in` observation.
- `cancelUnitCustody(custodyActionInput)`: either current participating warehouse before departure. In-transit/completed movement cannot be cancelled or silently undone; use a separately authorized return transfer.
- `getUnitCustodyTransfer(custodyGetInput)`, `listUnitCustodyHistory(custodyHistoryInput)`, `getWarehouseUnitCustody(custodyUnitInput)`: current `inventory.read`, site-limited history. List cursors are ascending immutable IDs; get returns the approved handoff plus only own-site event details.

Commands use durable operation IDs, expected revisions, the existing global alias/import gate before one unit advisory lock, and row CAS. Native transfer and alias-projection triggers use the same gate order, so alias revocation/ambiguity classification cannot change between validation and transition commit. Ordinary scan reads do not take this gate. Retrying the same operation returns its original receipt; changing its inputs fails. This is local command idempotency, not permission to replay an external effect. Publication/version changes elsewhere do not move a workflow run or grant execution to a different site.

An observation is independently attributed and must resolve uniquely to the same unit and a still-current approved alias, have the correct type and site, and occur after the preceding confirmed stage. Ambiguous/unidentified observations remain retained evidence and cannot complete custody. Scheduling/acceptance do not create observations. Recorded custody is past evidence, not a live sensor.

Before departure the database blocks active dispatch reservations, unfinished MARS intents, and labels without a settled cancellation or physical reconciliation. Native future label/MARS/dispatch writers share the unit lock and cannot create new work at an expected, in-transit, departed or cancelled destination. Existing effect settlements remain possible; unknown work is never replayed. These checks do not transfer old-site dispositions/printing rights.

## Required native integration seams

1. **Identity queries/creators:** read own-site private origin with `getUnitOriginInTransaction`; resolve all current visible aliases using `listSharedWarehouseAliasesInTransaction`. Existing detail/history/source queries retain their own-site RLS. Label context must include approved minimal shared aliases without copying private alias evidence. Raw shared identity compatibility fields are NULL.
2. **Report import:** use `(siteId,lpn)` upsert, consult `getPermittedImportedIdentityInTransaction` before identity creation/binding, retain foreign/ambiguous review conflicts. Unassociated reports may be saved without claiming physical identity; no order-only matching.
3. **New operational effects:** call `assertUnitOperationalCustodyInTransaction` after native permission checks, inside the original writer transaction, before exact-unit label preparation/dispatch, dispatch allocation, MARS preparation/start or disposition execution. `unestablished` preserves legacy association behavior; the native action still proves its own required physical evidence. Ordinary observations can remain evidence at a historical participating site, but cannot themselves change custody. Do not migrate active runs or reuse old-site grants.

Database predicates use bounded NOLOGIN owners `temco_custody_reader` and `temco_custody_writer`, explicit table grants, no runtime role membership and no PUBLIC function execution. Reader predicates return only current-site visibility, exact known-destination selectors or an import conflict boolean. Writer functions are trigger-only. The generic same-site link trigger retains its existing bounded owner and receives participation SELECT only. All unrelated parent relationships remain same-site; private history `siteId` remains immutable.
