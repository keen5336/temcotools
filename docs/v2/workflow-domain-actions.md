# Composing workflows from warehouse actions

Workflows now support an explicit `application` mode for registered internal application actions. `synthetic` remains the Receiving/local practice mode. External `live` mode remains unavailable. Adding an action ID, URL, provider name or capability string to a definition does not create executable authority: the complete action/configuration version and mode must match a server-registered contract, and current site/session/client capabilities are checked again for execution.

The mobile workflow manager shows the supported action catalog, exact pins, input/output schemas, current permission readiness and handoff limitations. The same catalog is returned by `workflows.list` and the shared `workflows.actions` query. Managers can copy the inventory-presence template, edit its bounded JSON, validate/test/publish and compose forms, conditions, actions and explicit confirmation steps without deployment. Draft tests can perform current authorized inventory reads; they never persist physical observations. Publishing and availability controls retain their existing current `workflows.manage` and recent password/MFA requirements.

Supported real building blocks:

- `warehouse.resolve` / `warehouse-resolve-v1` / `workflow-domain-v1` requires `inventory.read`. It calls the existing global alias resolver inside the workflow transaction, supporting LPN/MSN/serial/submission identifiers and namespace constraints. Its output preserves exact candidates, reported WMS rows, truncation and `physicalPresence: "not_determined"`. Order context does not select all related units, and ambiguous identifiers are not merged.
- `warehouse.observe` / `warehouse-observe-v1` / `workflow-domain-v1` requires `inventory.write`. This first workflow contract records **presence only**, through the existing `recordWarehouseObservationInTransaction` domain service. It does not receive, place, depart or change external WMS inventory. Inputs reference an earlier completed capture form, global lookup and later explicit confirmation. The server reads the actual recorded capture/confirmation; a literal `true`, supplied actor, fake device result or substituted identifier cannot replace that chain. It derives a stable native event ID from the pinned run/step/action version. The observation, step/result receipt and run revision commit atomically. If identifier links changed after lookup, the transaction rolls back and requires a fresh lookup instead of silently switching the unit.

`workflow.local.echo` remains available for bounded local JSON compositions. Synthetic Receiving actions are available only in `synthetic` mode. Unknown action/configuration versions, unqualified integrations and external printing/WMS/MARS actions remain blocked with a reason. No arbitrary network or JavaScript executor is exposed by these contracts.

Open `/tools/workflows` and choose **Look up and confirm observed presence**. Capture an identifier and the truthful manual/hardware-wedge method, optionally record the observed location, review the retained lookup and confirm the displayed physical-observation statement. Looking up an identifier or submitting the capture form alone writes no presence observation. A missing current `inventory.write` capability blocks the observation while retaining the captured facts and confirmation; a later authorized refresh can execute the pinned internal step. Each completed run retains its own original unit/alias context, actor, session/grant lineage and versioned intent. Repeating the original complete command envelope returns the original observation receipt without another write.

Camera/device steps expose a durable human/device handoff with an absolute action URL and exact reason. There is no qualified workflow capture-provider adapter yet. Such a step cannot complete from a caller-supplied boolean or `deviceVerified` field. A definition may explicitly allow `manualFallback: true`; the operator must then choose method `manual`, which is recorded as `deviceVerified: false`. Without that declared fallback, the step stays pending/blocked for the actual adapter. The browser is not assumed to expose a Zebra imager, and Scan Lab OCR is not connected to operational observations. A human/approval confirmation is an attributed claim, not device telemetry.

MCP uses the same `workflows.start`, `command`, `run` and catalog services. For the built-in application template, start with `{"operationId":"<new UUID>","template":"warehouse_presence"}`. Commands still require the originating run ID, immutable definition version, current revision and a stable command ID. A granted client can read or record only what its current scopes and warehouse membership allow; it cannot provide runtime snapshots, authorize a new device provider, settle an arbitrary adapter result or move a run to another warehouse.

Qualification uses `scripts/workflow-domain.integration.test.ts` against the exact disposable PostgreSQL database at `127.0.0.1:55439/temcotools_v2_warehouse_scope_test`. Synthetic source units/aliases exercise the real global lookup and native observation services, duplicate-command recovery, ambiguous original/replacement context, current capability/membership revocation, definition/action version isolation, draft no-write behavior, explicit handoffs/manual fallback and identifier-change rollback. No observation was invoked on the deployed pilot or production warehouse; no external endpoint, printer, live WMS adapter or actual handheld was exercised. Browser/MCP wire and deployment checks remain separately qualified by the coordinator.
