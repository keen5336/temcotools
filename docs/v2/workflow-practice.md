# Workflows and Receiving practice

This package implements durable, warehouse-scoped workflow definitions and local practice runs through the same application services for UI and MCP. It does **not** qualify live WMS reads/receipts/closure, physical printing, camera capture or operational Receiving. Adam's account and production data are not part of the synthetic fixtures.

Open `/tools/workflows`. The page shows its warehouse prominently and sends that site as selection context; the server rechecks current membership, individual session, client scope and capabilities. A saved run remains pinned to its originating site and immutable definition/action/configuration/provider/grant versions. Switching the surrounding application warehouse does not move a run. Operators see their own run list; managers with `workflows.manage` can inspect another run in the same warehouse, while commands remain attributed to the originating person. Cross-site IDs do not disclose run state.

Choose **Start Receiving practice**. This explicitly materializes the trusted built-in published template for that warehouse if needed; it does not give the operator arbitrary publication authority. Select `SYNTHETIC-INBOUND-001`, then scan or manually enter `SYNTHETIC-LPN-A01` and `SYNTHETIC-LPN-B01`. Select the truthful capture source. A repeated unit remains duplicate evidence and never counts twice. An unknown or ambiguous identifier is retained; a permitted reviewer must give a reason, and reviewing an exception does not supply a missing unit. Exact required units/quantities must be present before continuing.

The next action creates local simulated label ACKs. They do not satisfy the separate label-application confirmation. The explicit human confirmation advances the local simulator to individual unit receipt results and then closure only when the recorded completion rules pass. Scan, label ACK, physical confirmation, receipt and close remain separate records; every action/result and operator command is attributed. The entire exercise sends nothing to WMS or a printer and creates no warehouse inventory observations. Refreshing a run does not resend an intent.

The underlying kernel also retains partial unit successes when a simulated receipt is unknown, requires specific trusted reconciliation and prevents unknown close replay. These cases are exercised by native kernel tests. The public service does not accept caller-supplied adapter results or provide a pretend live reconciliation button; actual upstream reconciliation awaits the corresponding qualified contract. Do not confuse a successful default synthetic run with live qualification.

Workflow managers can create a local workflow or copy the Receiving template, edit bounded JSON on mobile, save, validate, test, publish, roll back and enable/disable. Draft saving permits unfinished bounded JSON; validation/publication require the typed definition schema. The editor supports forms with text/identifier/integer/boolean/choice fields, exact-unit or quantity scans, explicit human/device/camera/approval confirmations, forward conditions and parameter mappings to named version-pinned actions. There is no JavaScript evaluation, arbitrary network URL or graphical-editor dependency. Conditions can branch only forward; direct a branch past its alternative when needed. An initial local workflow demonstrates form input mapped to `workflow.local.echo`; this action returns its mapped JSON without external contact. Other action IDs stay unavailable until an actual supported adapter is registered and qualified.

Test runs execute only local adapters in memory; they do not create persistent operational runs. The MCP test action additionally accepts up to 100 safe operator commands for a scripted local trial. Publishing, rollback and availability changes require `workflows.manage` plus password and MFA confirmation within 10 minutes in `/account/security`. An MCP client uses its actual granted scope and the current human session; it cannot supply authenticator secrets or manufacture fresh authentication. Publication creates an immutable version and moves the published pointer. Later publications and rollbacks affect newly started runs; they do not rewrite active run definitions. Disabling a definition blocks further execution while preserving retained results.

The shared actions are `workflows.list`, `get`, `create`, `save`, `validate`, `test`, `publish`, `rollback`, `enabled`, `start`, `command`, `run` and `runs` under the `workflows.` prefix. UI requests POST JSON to `/api/application/<action>`; MCP resolves the same registered action and schema. Start with `workflows.start` input `{"operationId":"<new UUID>","template":"synthetic_receiving"}`. Inspect with `workflows.run` input `{"runId":"<returned run ID>"}`. A command supplies `runId`, a stable `commandId`, the original `expectedRevision`, `definitionVersionId` and a typed operator command. Retrying after a lost response must preserve that complete original envelope. Reusing an ID for different content conflicts; concurrent revisions cannot both commit. No `runtime`, provider grant or adapter-result fields are accepted from an operator.

Persistence consists of definition drafts/immutable versions, pinned run snapshots, a unique per-run command/event receipt and unique intent records for each step/attempt. Database row locks, current-authority checks and revision checks commit the run, intent/result and per-unit Receiving facts together. Only local deterministic simulation executes inside those transactions. A future live worker must commit its outbox first, then recheck membership, scope, exact original provider/grant and immutable action pins immediately before contact; it must retain unknown outcomes without automatic replay. The kernel integration contract is [lib/workflows/README.md](../../lib/workflows/README.md).

Live Receiving still needs the actual WMS upstream identity and warehouse binding, expected-delivery list/detail completeness and exact unit/line quantities, receipt idempotence/partial-success/unknown lookup contracts, closure semantics and specific live-trial authority. A real authorized label provider must preserve send/ACK/physical-outcome distinctions. DMP/Route Planner order identifiers or planned route legs do not supply those missing WMS contracts. Scan Lab OCR is a separate experiment and is not wired into this workflow.

Software validation uses `scripts/workflow-kernel.test.ts` and `scripts/workflow-service.integration.test.ts`. The latter runs only when `WAREHOUSE_SCOPE_TEST_DATABASE_URL` points exactly to the disposable PostgreSQL database `temcotools_v2_warehouse_scope_test` at `127.0.0.1:55439`; it creates synthetic users/sites/sessions and verifies real forced-RLS service transactions. It covers current revocation, MFA/scope denial, site isolation, definition version/rollback, concurrent command receipt behavior and complete local Receiving without inventory writes. Browser UI, deployed MCP wire and actual-device acceptance are separate checks owned by integration/deployment; no handheld performance result is claimed here.
