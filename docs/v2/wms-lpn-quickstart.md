# One read-only WMS LPN inquiry

Nov5 owner direction: prioritize a usable increment on the isolated dev URL; deploy independent software without waiting for Quill, all workflow contracts or physical scanner acceptance. This is a finite Connections increment, not Receiving redesign or upstream write authority.

Open [Connections → WMS LPN inquiry](https://temco-v2.chronchive.com/management/connections#wms-read-setup) with the existing account and correct warehouse. The original DMP page remains [available independently](https://temco-v2.chronchive.com/tools/api-relay).

## Ready to try now

1. Expand **Try the representative LPN fixture · no upstream send** and press **Preview synthetic LPN inquiry**. Integration management and inventory read permissions are required; the server rechecks them. Expect `execution: preview-only`, `sent: false`, `validatedOutput.lpn: SYNTHETIC-LPN-0001` and `reportedStatus: FIXTURE_ONLY`. This is a fixed sample, not a search of real inventory. It saves/publishes nothing and creates no connection or operational receipt.
2. The approved-provider panel now shows readable action names, the selected immutable version, semantic effect, qualification and typed input contract. Selecting a provider shows separate transport, identity and readiness reason/error. **Refresh provider status** explicitly reloads it.
3. For an actually approved and human-connected provider, **Prepare named action (no send)** commits the original intent. **Dispatch this original intent** sends that pinned work once. **Inspect private result / late evidence** reads the same ID and shows state/revision, HTTP status and declared-output validation, with the full private body in the existing result view. A schema-valid body alone does not prove the requested LPN, warehouse, business success or physical presence. No automatic retry or inference of receipt occurs.

The shared UI/MCP services are unchanged: `integrations.preview`, `connections.status`, `connections.runtime.*`, `connections.operation.prepare/claim/get`, `connections.operations`. MCP needs current site/capabilities and an explicit human named-read share for an established provider; it cannot activate the original work tab or approve sharing. The representative definition/input/output live in [wms-lpn-fixture.ts](../../lib/integrations/wms-lpn-fixture.ts). All endpoint/field names in that fixture are synthetic, not a Descartes contract.

## Smallest owner input for the real read

On the work machine, sign into the existing WMS browser interface yourself. Open the **actual LPN inquiry/detail screen**, enter one known LPN, and identify the screen/action that produced its result. We need:

- Exact browser origin and pathname, without query/fragment; screen/menu/action name and whether it really works in the browser versus opening native FMHH.
- That existing lookup's request method and relative path, sanitized input parameter names and encoding, plus a private body-only JSON/XML/text response and capture time. Do not send request headers, cookies, credentials, tokens, HAR or a package containing them. POST can be a read only when the actual action establishes read semantics; method alone does not.
- The **existing read** that returns the actual signed-in identity and warehouse, its body-only shape, and which evidenced warehouse value corresponds to the current Temco warehouse. Do not invent an identity endpoint or guess a warehouse identifier. Current generic identity extraction supports bounded JSON fields; HTML/XML identity or a new protocol requires a narrow reviewed adapter.

Use [Private Source Samples](https://temco-v2.chronchive.com/tools/dmp-samples), source **other operational export**, to upload a reviewed body-only JSON/XML/CSV with method/day/as-of provenance. The existing private intake is bounded to2MiB and current user/site; unknown timezone stays unknown. A screen name plus the one sanitized lookup/identity shape is enough to start. Do not upload raw customer/source material to Git or public chat. A private export can establish fields while the live connection remains unverified.

If **LPN inquiry is native-FMHH-only**, the browser injector has nowhere to execute that action. This changes the capture/transport step: first identify an actually supported browser inquiry/export or documented approved interface. Do not copy the app's session or guess its network calls. A native bridge is not part of this increment. Existing manual inventory imports and DMP continue to work.

## After evidence is available

A platform admin with fresh password + MFA drafts and explicitly qualifies the evidenced identity and LPN READ actions. Publish the **generic approved-provider executor** payload with those exact named keys and actual approved origin; publish its exact origin/path site profile. Select a published action in Connections and **Register unqualified browser configuration**; registration alone does not connect it. Under **Platform identity and warehouse contract configuration**, pin provider ID/current revision, profile ID/revision, payload version/hash, identity/business action versions, identity inputs, actual JSON subject/warehouse paths and evidenced upstream warehouse. The existing version panels expose those IDs. See [connection guide](provider-connection-guide.md) and [runtime contract](provider-runtime.md) for exact fields.

The human then runs **Connect TemcoTools** on that original signed-in WMS page, approves the exact provider/current warehouse in its popup, and keeps the tab open. Both actual location and the identity response must verify. Human consent grants only the named read to the intended session/device/MCP client; DMP authority does not carry over. Refresh Connections, choose the approved LPN action, enter its **evidenced** typed input, prepare/dispatch once and compare its private receipt with that exact LPN on the screen. Record the capture/as-of and exact action/config versions. Keep unknown results without replay; inspect/reconcile before any new work.
